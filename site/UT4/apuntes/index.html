    Apuntes · Implantación de CMS¶

    0. Antes de empezar: qué vas a aprender de verdad aquí¶

    Esta unidad no va de memorizar pantallas del panel de WordPress.

    Lo importante es entender este proceso:

    1. una organización necesita publicar contenidos sin programar cada página desde cero;
    2. se selecciona un CMS adecuado para ese caso;
    3. se despliega sobre una arquitectura mínima;
    4. se completa la instalación;
    5. se configura para que sea usable, segura y mantenible;
    6. se prueba;
    7. y solo entonces se considera publicable.

    Si entiendes bien ese ciclo, luego todo encaja: - por qué existe un CMS, - por qué necesita base de datos, - por qué tiene usuarios, roles y plugins, - por qué no basta con instalarlo “como salga”, - y por qué un administrador de sistemas debe verlo como una implantación real, no como un juguete de aula.

    1. ¿Qué es un CMS?¶

    Un CMS es un Content Management System, es decir, un sistema de gestión de contenidos.

    Su objetivo es permitir que una organización publique y mantenga contenidos web sin tener que programar cada página manualmente.

    Dicho de forma sencilla¶

    Un CMS es una aplicación web ya preparada para que alguien pueda:

    • crear páginas;
    • editar textos;
    • subir imágenes;
    • organizar menús;
    • gestionar usuarios;
    • instalar extensiones;
    • y publicar un sitio con una base técnica ya resuelta.

    Qué problema resuelve¶

    Sin CMS, una organización pequeña o mediana tendría que elegir entre dos extremos:

    • crear un sitio completamente a medida;
    • o mantener manualmente archivos HTML, CSS y otros recursos.

    Eso suele ser lento, caro y poco escalable para el día a día editorial.

    Un CMS resuelve justo ese problema:

    • separa contenido y gestión;
    • ofrece un panel de administración;
    • reparte tareas entre perfiles técnicos y no técnicos;
    • y acelera mucho la puesta en marcha de un sitio.

    Lo que un CMS no hace por arte de magia¶

    Un CMS no elimina la técnica.
    Solo la encapsula mejor.

    Sigue habiendo:

    • servidor web;
    • PHP u otra tecnología de aplicación;
    • base de datos;
    • archivos persistentes;
    • copias de seguridad;
    • seguridad;
    • actualización;
    • y pruebas.

    Mini ejercicio 1¶

    Responde por escrito:

    1. ¿Qué significa CMS?
    2. ¿Qué problema real resuelve en una empresa o institución?
    3. Nombra tres tareas que un editor puede hacer con un CMS sin tocar código.

    2. ¿Cuándo tiene sentido usar un CMS y cuándo no?¶

    No todas las webs necesitan un CMS.

    Casos donde un CMS suele encajar muy bien¶

    • sitio corporativo con varias secciones;
    • blog o revista digital;
    • portal de noticias;
    • web de centro educativo;
    • intranet sencilla;
    • tienda online con catálogo;
    • portal institucional con varios perfiles editores.

    Casos donde quizá no es la mejor opción¶

    • una landing muy pequeña y estática;
    • una aplicación web de negocio con lógica muy específica;
    • un frontend desacoplado con requisitos muy concretos;
    • una API pura sin panel editorial clásico;
    • un micrositio mínimo que apenas cambia.

    Regla práctica¶

    Un CMS tiene sentido cuando el valor está en gestionar contenidos y usuarios con rapidez, no en construir toda la lógica desde cero.

    Una metáfora útil¶

    Piensa en la diferencia entre:

    • fabricar un mueble desde tablones;
    • o montar un sistema modular bien diseñado.

    Si necesitas algo muy específico, quizá construyas desde cero.
    Si necesitas algo funcional, mantenible y rápido de poner en marcha, lo modular tiene mucha ventaja.

    3. Arquitectura básica de un CMS¶

    Para un alumno de ASIR es importante ver un CMS como una arquitectura, no solo como un panel.

    flowchart TD
    A[Navegador del visitante] --> B[Servidor web + CMS]
    C[Navegador del editor] --> D[Panel de administración]
    D --> B
    B --> E[Base de datos]
    B --> F[Archivos persistentes]

    Qué suele haber por debajo¶

    1. Servidor web¶

    Es el componente que recibe la petición HTTP y sirve la aplicación.

    En nuestro caso, con WordPress, normalmente aparecerá como un entorno con:

    • Apache o Nginx;
    • PHP;
    • la aplicación WordPress;
    • y acceso a su base de datos.

    2. Aplicación CMS¶

    Es el propio sistema gestor:

    • WordPress,
    • Drupal,
    • PrestaShop,
    • Moodle,
    • MediaWiki,
    • u otro similar.

    3. Base de datos¶

    El CMS guarda en base de datos gran parte de la información:

    • usuarios;
    • páginas;
    • entradas;
    • menús;
    • ajustes;
    • taxonomías;
    • configuraciones;
    • y mucha metainformación.

    4. Archivos persistentes¶

    Además de la base de datos, un CMS suele necesitar almacenamiento para:

    • imágenes y medios subidos;
    • extensiones;
    • temas;
    • cachés;
    • y configuraciones auxiliares.

    Conclusión importante¶

    Cuando implantas un CMS, no estás instalando “una página web”.
    Estás levantando una aplicación con estado.

    Mini ejercicio 2¶

    Explica con tus palabras qué papel tiene cada uno de estos elementos en un CMS:

    1. servidor web;
    2. base de datos;
    3. almacenamiento persistente.

    4. Tipos de CMS según la funcionalidad principal¶

    Uno de los criterios de evaluación del RA exige que sepas clasificar gestores de contenidos según la función principal del sitio que permiten gestionar.

    No se trata de memorizar listas gigantes, sino de saber orientar la elección.

    4.1. CMS de propósito general o editorial¶

    Son los más típicos para:

    • webs corporativas;
    • blogs;
    • páginas de servicios;
    • portales con secciones editoriales.

    Ejemplo claro¶

    WordPress

    Puntos fuertes: - implantación rápida; - curva de entrada razonable; - enorme ecosistema; - válido para muchos sitios pequeños y medianos.

    4.2. CMS orientados a portales complejos y modelado de contenido¶

    Suelen encajar mejor cuando hay:

    • estructuras de contenido más complejas;
    • permisos más finos;
    • flujos editoriales más exigentes;
    • sitios institucionales o grandes portales.

    Ejemplo claro¶

    Drupal

    Puntos fuertes: - modelado potente; - enfoque más estructurado; - buena base para portales complejos.

    4.3. CMS de comercio electrónico¶

    Se centran en:

    • catálogo;
    • pedidos;
    • clientes;
    • pagos;
    • stock;
    • promociones.

    Ejemplos habituales¶

    • PrestaShop
    • Magento / Adobe Commerce
    • WooCommerce como extensión sobre WordPress

    4.4. LMS o plataformas de aprendizaje¶

    Aunque no siempre se nombren como CMS en sentido clásico, gestionan contenidos formativos y usuarios.

    Ejemplo claro¶

    Moodle

    Se centra en: - cursos; - alumnado; - actividades; - evaluación; - seguimiento.

    4.5. Wikis y documentación colaborativa¶

    Se orientan a conocimiento compartido y edición colaborativa.

    Ejemplo claro¶

    MediaWiki

    Útil para: - documentación; - base de conocimiento; - intranets documentales.

    4.6. CMS desacoplados o headless¶

    Gestionan contenido en backend y lo exponen a otros frontends o APIs.

    No son el foco de esta UT, pero conviene saber que existen.

    Tabla rápida de orientación¶

    Tipo Ejemplos Suele encajar en Idea clave
    CMS general/editorial WordPress webs corporativas, blogs, sitios de contenido rapidez y ecosistema
    CMS portal/estructurado Drupal portales complejos, institucionales estructura y modelado
    CMS e-commerce PrestaShop, Magento tiendas online catálogo y venta
    LMS Moodle enseñanza y formación cursos y seguimiento
    Wiki/documentación MediaWiki conocimiento compartido colaboración documental

    1. una academia que necesita cursos, tareas y seguimiento;
    2. una tienda con catálogo y carrito;
    3. una web corporativa con blog y páginas de servicios;
    4. una base interna de documentación técnica.

    5. Criterios de selección de un CMS¶

    Elegir un CMS no es una cuestión de gustos.
    Es una decisión técnica y funcional.

    Preguntas que conviene hacerse¶

    ¿Qué tipo de sitio necesito?¶

    No es lo mismo:

    • un blog,
    • una web corporativa,
    • una tienda,
    • un portal institucional,
    • o una plataforma educativa.

    ¿Quién va a editar el contenido?¶

    • un perfil técnico;
    • personal administrativo;
    • profesorado;
    • departamento de comunicación;
    • múltiples editores con distintos roles.

    ¿Qué complejidad de contenidos voy a manejar?¶

    • páginas simples;
    • noticias;
    • taxonomías;
    • fichas con muchos campos;
    • permisos por secciones;
    • flujos de revisión.

    ¿Qué rapidez de implantación necesito?¶

    A veces la prioridad es salir rápido.
    Otras veces importa más la estructura a largo plazo.

    ¿Qué ecosistema y soporte tiene?¶

    • temas;
    • plugins o módulos;
    • documentación;
    • comunidad;
    • facilidad para encontrar profesionales.

    ¿Qué exige la operación posterior?¶

    • actualizaciones;
    • backups;
    • mantenimiento;
    • formación de editores;
    • seguridad;
    • observabilidad básica.

    Error típico¶

    Elegir un CMS solo por fama.

    La fama ayuda, pero la pregunta correcta es:

    ¿Encaja con este caso concreto y con los recursos reales de quien lo va a operar?

    6. WordPress como CMS de referencia en esta UT¶

    En esta unidad nos centraremos principalmente en WordPress.

    ¿Por qué WordPress aparece aquí?¶

    Porque sigue siendo una referencia muy habitual en implantación web y cuenta con una documentación amplia sobre puesta en marcha, administración y seguridad. Además, su enfoque encaja muy bien con una UT donde importa tanto la implantación como la configuración posterior.

    Qué hace especialmente útil a WordPress en esta unidad¶

    • permite una implantación bastante rápida;
    • encaja muy bien en sitios corporativos, blogs y webs de contenido;
    • es fácil de contextualizar profesionalmente;
    • tiene una arquitectura comprensible para alumnado de ASIR;
    • permite trabajar instalación, configuración, seguridad inicial, pruebas y publicación sin una complejidad desbordante.

    Lo que no conviene pensar¶

    No conviene caer en dos extremos:

    • “WordPress sirve para todo”.
    • “WordPress es solo un blog”.

    La realidad es más útil y más matizada:

    • sirve muy bien para muchos casos;
    • pero no es la respuesta universal a cualquier sistema web;
    • y su calidad final depende muchísimo de cómo se implante y se mantenga.

    Componentes que suelen aparecer en una implantación WordPress¶

    • contenedor o servidor con WordPress;
    • servicio de base de datos;
    • volúmenes persistentes;
    • configuración inicial del sitio;
    • temas y plugins;
    • usuarios y roles;
    • pruebas;
    • y una estrategia mínima de publicación y mantenimiento.

    Mini ejercicio 4¶

    Escribe tres razones por las que WordPress tiene sentido como CMS principal en esta UT y una razón por la que no debería elegirse “por defecto” para cualquier proyecto.

    7. Comparación breve: WordPress y Drupal¶

    No vamos a convertir esta UT en una unidad de Drupal, pero sí conviene que sepas compararlo con WordPress, porque ambos aparecen con frecuencia en contextos profesionales y ambos disponen de documentación oficial de instalación y uso. Además, Drupal suele presentarse con un enfoque más técnico y estructurado en su puesta en marcha.

    WordPress suele destacar cuando...¶

    • necesitas rapidez de implantación;
    • el sitio es editorial o corporativo;
    • quieres una curva de entrada razonable;
    • el ecosistema disponible te ayuda mucho.

    Drupal suele destacar cuando...¶

    • el contenido tiene una estructura más exigente;
    • los permisos y el modelado importan mucho;
    • hay mayor complejidad institucional o portal.

    Una comparación muy práctica¶

    Aspecto WordPress Drupal
    Entrada inicial más rápida en muchos casos más exigente
    Curva de aprendizaje más amable para empezar más pronunciada
    Enfoque habitual editorial/generalista estructurado/portal
    Ecosistema enorme y muy visible sólido, más técnico
    Encaje típico en esta UT ideal como eje principal útil para contraste técnico

    Conclusión realista¶

    En una FP de ASIR, WordPress es muy buen eje para aprender la competencia de implantación.
    Drupal aporta contraste y criterio de selección.

    Mini ejercicio 5¶

    Indica en qué caso elegirías mejor WordPress y en cuál Drupal:

    1. sitio corporativo pequeño de una academia;
    2. portal institucional con tipos de contenido y permisos más complejos.

    Justifica cada respuesta en dos o tres líneas.

    8. Opciones de implantación de un CMS¶

    Un CMS puede implantarse de varias formas.

    8.1. Hosting compartido¶

    Es frecuente en entornos pequeños o de bajo coste.

    Ventajas: - sencillo; - barato; - rápido de arrancar.

    Inconvenientes: - menos control; - más limitaciones; - peor reproducibilidad; - menos parecido a un entorno administrado por ASIR.

    8.2. Servidor propio o VPS¶

    Da más control sobre:

    • sistema;
    • servicios;
    • red;
    • backups;
    • publicación;
    • seguridad.

    8.3. Contenedores¶

    Para esta UT es una opción muy buena porque permite:

    • reproducibilidad;
    • aislamiento razonable;
    • despliegue rápido;
    • estructura clara por servicios;
    • y facilidad para reiniciar, borrar o rehacer entornos.

    Por eso aquí tiene mucho sentido usar Docker Compose.

    8.4. PaaS o soluciones gestionadas¶

    Existen, pero no son el centro de esta unidad.

    Idea clave¶

    No estamos usando Docker Compose por moda, sino porque ayuda a que el alumnado vea claramente:

    • qué servicios hay;
    • cómo se relacionan;
    • qué datos deben persistir;
    • y cómo dejar un entorno replicable.

    9. WordPress con Docker Compose¶

    Docker Compose encaja muy bien en esta unidad porque obliga a pensar en servicios, persistencia, puertos y comprobaciones de funcionamiento dentro de una aplicación multicontenedor.

    9.1. Servicios mínimos que necesitamos¶

    Para una implantación básica de WordPress necesitamos, como mínimo:

    1. un servicio de base de datos;
    2. un servicio WordPress;
    3. volúmenes persistentes para no perder datos al recrear contenedores.

    Arquitectura mínima¶

    flowchart LR
    A[Navegador] --> B[WordPress]
    B --> C[MariaDB]
    B --> D[Volumen de WordPress]
    C --> E[Volumen de base de datos]

    9.2. Ejemplo mínimo de docker-compose.yml¶

    services:
  db:
    image: mariadb:11
    container_name: ut4_wp_db
    restart: unless-stopped
    environment:
      MARIADB_DATABASE: wordpress
      MARIADB_USER: wordpress
      MARIADB_PASSWORD: wordpress
      MARIADB_ROOT_PASSWORD: rootpass
    volumes:
      - db_data:/var/lib/mysql

  wordpress:
    image: wordpress:latest
    container_name: ut4_wp_app
    restart: unless-stopped
    depends_on:
      - db
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: wordpress
      WORDPRESS_DB_NAME: wordpress
    volumes:
      - wp_data:/var/www/html

volumes:
  db_data:
  wp_data:

    Qué debes entender de este fichero¶

    Servicio db¶

    Levanta la base de datos y crea:

    • base de datos;
    • usuario;
    • contraseña;
    • password de root.

    Servicio wordpress¶

    Levanta WordPress y le indica cómo conectar con la base de datos.

    WORDPRESS_DB_HOST¶

    Aquí aparece uno de los errores más típicos de toda la UT.

    Dentro de Compose, el host no debe ser localhost, sino el nombre del servicio:

    db

    o, si se especifica puerto:

    db:3306

    Por qué localhost sería un error¶

    Porque desde el contenedor de WordPress, localhost significa “este mismo contenedor”, no el contenedor de base de datos.

    Mini ejercicio 6¶

    Observa el docker-compose.yml anterior y responde:

    1. ¿Qué servicio atiende las peticiones web?
    2. ¿Qué servicio guarda los datos?
    3. ¿Qué dos elementos hacen que los datos no se pierdan al reiniciar el entorno?
    4. ¿Por qué WORDPRESS_DB_HOST no debe ser localhost?

    9.3. Variables, puertos y persistencia¶

    Puerto publicado¶

    En el ejemplo:

    ports:
  - "8080:80"

    significa:

    • puerto 8080 en el host;
    • puerto 80 dentro del contenedor.

    Por tanto, el sitio será accesible desde:

    http://localhost:8080

    Volúmenes¶

    Los volúmenes son fundamentales.

    Sin ellos, podrías perder: - la base de datos; - los archivos de WordPress; - medios subidos; - parte de la configuración.

    Recomendación docente¶

    En esta UT conviene que el alumnado pruebe una vez el efecto de levantar y bajar el entorno sin borrar volúmenes, y otra vez el efecto de hacer down -v, para que vea la diferencia entre:

    • parar servicios;
    • y destruir el estado.

    9.4. Puesta en marcha¶

    Una secuencia típica sería:

    docker compose up -d
docker compose ps
docker compose logs -f wordpress

    Después se abre en navegador:

    http://localhost:8080

    y se completa el instalador web.

    9.5. Qué hace realmente el instalador inicial¶

    En el instalador sueles definir:

    • idioma;
    • título del sitio;
    • usuario administrador;
    • contraseña;
    • correo;
    • visibilidad inicial o ajustes relacionados.

    Aunque visualmente parece “un asistente sencillo”, en realidad estás:

    • conectando la aplicación a su estado;
    • creando la estructura base del sitio;
    • generando un administrador;
    • y dejando el CMS listo para entrar en operación.

    10. Configuración inicial de WordPress¶

    La instalación no termina cuando aparece el panel.

    Ese es otro error clásico.

    Instalar es solo el principio.
    Después hay que configurar con criterio.

    10.1. Ajustes generales¶

    Nada más entrar, conviene revisar al menos:

    • título del sitio;
    • descripción corta o lema;
    • idioma;
    • zona horaria;
    • formato de fecha y hora;
    • correo principal del sitio.

    Esto parece pequeño, pero da pistas muy rápidas de si la implantación se ha hecho con cabeza o deprisa.

    10.2. Estructura inicial de contenido¶

    Para una implantación mínima razonable conviene dejar, al menos:

    • una página de inicio;
    • una página de servicios o equivalente;
    • una página de contacto;
    • un menú de navegación básico.

    ¿Por qué esto importa?¶

    Porque la UT no trata solo de “que el login funcione”, sino de implantar un sitio utilizable.

    10.3. Enlaces permanentes¶

    Una revisión muy importante es la de permalinks o enlaces permanentes.

    Si se dejan con una estructura poco amigable, el sitio funciona, sí, pero la publicación es peor:

    • URLs menos claras;
    • peor legibilidad;
    • peor impresión profesional.

    Una configuración habitual y bastante razonable es:

    • nombre de la entrada
    • o una estructura equivalente simple y legible

    10.4. Usuarios y roles¶

    Un CMS tiene sentido, entre otras cosas, porque reparte tareas.

    En WordPress conviene distinguir entre perfiles como:

    • administrador;
    • editor;
    • autor;
    • colaborador;
    • suscriptor.

    Idea importante¶

    No todo el mundo debe ser administrador.

    Ese es un error muy común en sitios pequeños: - se crea un usuario y se le da acceso total “por comodidad”.

    Desde el punto de vista de implantación y seguridad, eso es mala práctica.

    10.5. Temas¶

    Un tema define gran parte de la presentación del sitio.

    En esta UT no vamos a desarrollar temas, pero sí debemos entender que:

    • elegir un tema también es una decisión de implantación;
    • conviene usar uno estable y razonable;
    • no hay que instalar temas al azar solo porque “quedan bonitos”.

    10.6. Plugins¶

    Los plugins amplían la funcionalidad.

    Son útiles, pero también introducen: - mantenimiento; - riesgo; - dependencia; - y posibles problemas de compatibilidad.

    Regla sana para esta UT¶

    Instala pocos y con propósito claro.

    Un plugin no es un trofeo.
    Es una pieza adicional que habrá que mantener.

    Haz una checklist mínima de configuración inicial para un WordPress recién instalado.
    Incluye al menos seis puntos y ordénalos de más urgente a menos urgente.

    11. Seguridad inicial del CMS¶

    La seguridad inicial de WordPress no depende de una única opción mágica, sino de un conjunto de decisiones sensatas: actualizar, revisar usuarios y roles, limitar superficie innecesaria y publicar con criterios mínimos de protección.

    En esta UT no vamos a hacer un hardening completo de producción, pero sí una capa inicial razonable.

    11.1. Actualizaciones¶

    Lo primero y más básico:

    • WordPress actualizado;
    • temas actualizados;
    • plugins actualizados.

    No tiene sentido implantar deprisa y dejar desactualizado desde el minuto uno.

    Además, conviene transmitir al alumnado que el mantenimiento activo no es una recomendación decorativa, sino una parte real del ciclo de vida del CMS.

    11.2. Usuarios y contraseñas¶

    Medidas mínimas: - no usar credenciales triviales; - crear usuarios con el rol justo; - separar administración y edición si el caso lo pide; - no compartir la misma cuenta entre varias personas.

    11.3. Comentarios, registro y superficie de ataque¶

    Si el sitio no necesita comentarios, no tiene por qué dejarlos abiertos.

    Si no necesitas registro público de usuarios, no tiene sentido abrirlo.

    Regla práctica¶

    Todo lo que no aporta valor al caso real y aumenta superficie de ataque debe revisarse.

    11.4. No indexar durante construcción¶

    Mientras el sitio está en montaje o pruebas, suele ser buena idea evitar que se indexe prematuramente.

    Eso no sustituye a una seguridad real, pero sí evita publicar accidentalmente una web a medias.

    11.5. HTTPS y entorno publicado¶

    Siempre que el entorno lo permita, una publicación seria debería priorizar HTTPS para proteger accesos y visitantes. En aula puede que no se monte TLS completo, pero el criterio debe quedar claro.

    11.6. Mostrar errores y depuración¶

    En producción no conviene mostrar errores detallados al público.
    En entornos publicados no conviene mostrar errores detallados al público.

    Qué implica esto en la UT¶

    • en desarrollo puedes usar logs y depuración;
    • en publicación debes evitar mostrar información sensible.

    Mini ejercicio 8¶

    Indica si cada medida encaja o no en una seguridad inicial razonable y justifica muy brevemente:

    1. dejar todos los usuarios como administradores;
    2. actualizar núcleo, plugins y temas;
    3. abrir comentarios si el sitio no los necesita;
    4. usar contraseñas robustas;
    5. publicar una web en obras sin revisarla.

    12. Pruebas de funcionamiento¶

    Implantar no es solo levantar servicios y entrar al panel.
    Hay que probar.

    12.1. Qué se debe probar como mínimo¶

    Pruebas técnicas mínimas¶

    • el contenedor de WordPress arranca;
    • la base de datos responde;
    • el sitio carga;
    • el panel de administración es accesible;
    • no aparecen errores graves.

    Pruebas funcionales mínimas¶

    • se puede iniciar sesión;
    • las páginas creadas se ven;
    • el menú funciona;
    • el rol editor tiene permisos coherentes;
    • el visitante ve lo que tiene que ver;
    • el sitio mantiene su estado tras reinicio de contenedores.

    Pruebas de publicación básica¶

    • la URL o IP/puerto se abre desde el equipo esperado;
    • el frontend responde;
    • el panel responde;
    • no se han roto rutas o menús;
    • la configuración principal sigue intacta.

    12.2. Smoke test sencillo¶

    Un smoke test es una comprobación rápida para detectar si lo esencial funciona.

    Ejemplo simple para esta UT:

    1. abrir portada;
    2. abrir una página secundaria;
    3. iniciar sesión;
    4. comprobar el menú;
    5. revisar ajustes principales;
    6. reiniciar contenedores;
    7. volver a comprobar portada y panel.

    12.3. Por qué esto importa tanto¶

    Porque uno de los errores más frecuentes en alumnado técnico es pensar:

    “Como el sitio se ve, ya está”.

    No.
    Un CMS puede “verse” y, aun así, tener problemas de:

    • permisos;
    • persistencia;
    • publicación;
    • rutas;
    • roles;
    • o configuración incoherente.

    13. Publicación básica del CMS¶

    La publicación no siempre significa “ponerlo en Internet para todo el mundo” en esta UT.

    Aquí la idea es que el sitio quede:

    • accesible por una URL o IP/puerto;
    • coherente en su configuración;
    • y listo para una salida razonable de preproducción o publicación básica.

    13.1. Niveles posibles de publicación en esta unidad¶

    Nivel 1. Publicación local controlada¶

    El sitio es accesible desde el propio host por una URL clara.

    Ejemplo: 

    http://localhost:8080

    Nivel 2. Publicación en red local¶

    El sitio es accesible desde otro equipo de la red del aula usando la IP del host.

    Ejemplo: 

    http://192.168.1.50:8080

    Nivel 3. Publicación en entorno del centro o servidor¶

    Si el centro dispone de infraestructura, podría exponerse por dominio interno o subdominio.

    No es obligatorio en todos los contextos, pero sí conviene comprender el salto conceptual.

    13.2. Qué revisar antes de publicar¶

    • URL correcta;
    • estructura básica finalizada;
    • usuarios y roles revisados;
    • actualizaciones al día;
    • comentarios o registros innecesarios desactivados;
    • visibilidad del sitio decidida con criterio;
    • pruebas mínimas completadas.

    13.3. Error clásico¶

    Confundir “se abre en mi navegador” con “está correctamente publicado”.

    Eso no es suficiente.
    Hay que comprobar que:

    • el entorno es el correcto;
    • los datos persisten;
    • el sitio es navegable;
    • y la configuración no está a medio hacer.

    14. Errores típicos y diagnóstico rápido¶

    14.1. Error: WordPress no conecta con la base de datos¶

    Causas típicas: - host mal indicado; - usuario o contraseña incorrectos; - base de datos aún no preparada; - servicio db caído.

    Pista de diagnóstico¶

    Revisa: - docker compose ps - docker compose logs db - docker compose logs wordpress

    14.2. Error: he reiniciado y he perdido todo¶

    Suele ocurrir cuando: - no había volúmenes; - o se ha ejecutado docker compose down -v.

    Idea clave¶

    Parar contenedores no es lo mismo que destruir el estado.

    14.3. Error: funciona el frontend, pero no el panel¶

    Posibles causas: - configuración incompleta; - rutas mal resueltas; - problema de permisos; - error temporal de aplicación; - plugin o tema conflictivo.

    14.4. Error: el sitio se ve muy “vacío”¶

    No es un error técnico, pero sí de implantación incompleta.

    Una implantación mínima profesional no debería quedarse en: - portada por defecto; - entrada “Hello world”; - comentario de prueba; - menú inexistente.

    14.5. Error: demasiados plugins¶

    Cuando aparecen muchos plugins innecesarios, suele ocurrir esto: - mayor complejidad; - más actualizaciones; - más riesgo; - peor trazabilidad.

    14.6. Error: todo el mundo es admin¶

    Esto simplifica hoy y complica mañana.

    Es cómodo, pero mala práctica.

    15. Buenas prácticas básicas para esta UT¶

    • levantar el CMS en un entorno reproducible;
    • separar servicios con claridad;
    • usar persistencia;
    • documentar el puerto y la URL de acceso;
    • revisar ajustes generales nada más instalar;
    • configurar una estructura mínima de contenido;
    • limitar roles según necesidad real;
    • instalar pocos plugins y con propósito;
    • actualizar antes de dar por bueno;
    • probar antes de publicar;
    • dejar evidencia de lo hecho.

    16. Resumen final de la unidad¶

    Un CMS no es solo una herramienta para escribir páginas.
    Es una aplicación web completa que debes saber implantar con criterio.

    En esta UT has visto que:

    • un CMS resuelve necesidades editoriales muy comunes;
    • hay varios tipos según la función principal del sitio;
    • WordPress encaja muy bien como eje de aprendizaje;
    • la implantación técnica importa tanto como la parte visual;
    • seguridad, pruebas y publicación no son extras, sino parte del trabajo;
    • y un entorno reproducible con Docker Compose ayuda mucho a aprender bien.
