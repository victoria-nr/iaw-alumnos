    Apuntes de la UT3¶

    1. Por qué una aplicación web necesita una base de datos¶

    En la UT2 hemos trabajado con PHP como lenguaje de servidor. Ya sabíamos:

    • recibir datos desde formularios;
    • tomar decisiones;
    • generar HTML dinámico;
    • reutilizar ficheros y lógica.

    Sin embargo, todo eso tenía una limitación clara: los datos no persistían.

    Si un usuario rellenaba un formulario y nosotros no guardábamos esa información en ningún sitio, la aplicación no tenía memoria. Era como atender una llamada telefónica, escuchar los datos y olvidarlos al colgar.

    Metáfora útil¶

    • PHP es el recepcionista que atiende.
    • La base de datos es el archivador bien organizado.
    • El navegador es quien pide información o la envía.

    Si el recepcionista atiende muy bien pero no apunta nada en el archivador, el sistema no escala ni sirve para procesos reales.

    Casos reales donde esto importa¶

    • una tienda online necesita guardar catálogo, clientes y pedidos;
    • una web corporativa puede necesitar guardar formularios de contacto;
    • una app de reservas necesita registrar disponibilidad y reservas confirmadas;
    • una intranet necesita guardar incidencias, usuarios y estados.

    Conclusión

    En una aplicación web, la base de datos no es un añadido decorativo. Es una parte central del sistema.

    Mini ejercicio 1¶

    Piensa en tres aplicaciones web que uses de forma habitual.
    Para cada una, responde:

    1. ¿Qué datos necesita guardar?
    2. ¿Qué pasaría si no tuviera base de datos?
    3. ¿Qué operaciones CRUD imaginas que realiza por detrás?

    2. Qué es un SGBD y cuáles aparecen habitualmente en entornos web¶

    Un SGBD es un Sistema Gestor de Bases de Datos. Es el software que permite:

    • crear bases de datos;
    • definir tablas;
    • insertar, consultar, modificar y borrar datos;
    • controlar usuarios y permisos;
    • asegurar integridad y consistencia.

    Algunos SGBD habituales en el mundo web¶

    SGBD Uso habitual Ventajas Inconvenientes
    MariaDB / MySQL Hosting tradicional, CMS, aplicaciones web generales Muy extendido, fácil de encontrar, gran documentación No siempre es el mejor para todos los casos
    PostgreSQL Aplicaciones con mayor complejidad de datos o requisitos avanzados Muy robusto, potente y completo Suele introducir algo más de complejidad inicial
    SQLite Prototipos, apps pequeñas, pruebas, herramientas embebidas Muy simple, sin servidor separado No está orientado a escenarios multiusuario intensivos
    SQL Server Entornos Microsoft Integración empresarial Menos habitual en escenarios web ligeros Linux
    Oracle Grandes entornos corporativos Muy potente Complejidad y coste

    ¿Por qué en esta UT usaremos SQLite y MariaDB/MySQL?¶

    Porque juntos cubren dos escenarios didácticos muy útiles:

    SQLite¶

    Nos ayuda a centrar la atención en:

    • la lógica PHP;
    • PDO;
    • la estructura CRUD;
    • el ciclo completo sin depender de un servidor de base de datos aparte.

    MariaDB/MySQL¶

    Nos permite introducir:

    • conexiones reales por host, base de datos, usuario y contraseña;
    • permisos y seguridad;
    • herramientas de administración como Adminer o phpMyAdmin;
    • una situación más cercana a producción.

    Decisión metodológica

    No intentamos estudiar todos los SGBD del mercado. Elegimos dos que permiten aprender bien el patrón general y transferirlo después.

    Error típico¶

    Pensar que “aprender bases de datos” en esta UT significa estudiar SQL de forma abstracta y aislada.

    No.
    En esta UT el SQL aparece al servicio de una aplicación PHP.

    3. Dónde encaja la base de datos en una aplicación web¶

    La secuencia simplificada suele ser esta:

    1. el usuario abre una página o envía un formulario;
    2. el servidor ejecuta código PHP;
    3. PHP consulta o modifica la base de datos;
    4. PHP construye una respuesta HTML;
    5. el navegador la muestra.
    flowchart TD
    A[Usuario solicita una acción] --> B[PHP recibe la petición]
    B --> C{¿Necesita datos?}
    C -- Sí --> D[Consulta o actualiza la BD]
    D --> E[PHP procesa resultado]
    C -- No --> E
    E --> F[Genera HTML]
    F --> G[Respuesta al navegador]

    Qué hace realmente PHP aquí¶

    PHP no “es” la base de datos.
    PHP actúa como puente:

    • decide qué consulta ejecutar;
    • prepara parámetros;
    • recoge los resultados;
    • transforma esos datos en HTML útil.

    Ejemplo mental¶

    Supón una agenda de contactos.

    • El usuario pulsa “Ver contactos”.
    • PHP pide a la base de datos todos los contactos.
    • La base de datos devuelve filas.
    • PHP recorre esas filas y genera una tabla HTML.

    Si el usuario pulsa “Guardar contacto”:

    • PHP recibe nombre, email y teléfono;
    • valida;
    • ejecuta un INSERT;
    • redirige o muestra mensaje de éxito.

    4. La problemática de conectar PHP con distintos SGBD¶

    Aquí aparece un problema muy real.

    Aunque muchos gestores usan SQL, no son idénticos:

    • cambian detalles del sistema;
    • cambian formas de conexión;
    • cambian algunas funciones y tipos;
    • cambian herramientas de administración.

    Si atamos toda nuestra aplicación a una única forma de acceso muy específica, nos costará más:

    • cambiar de gestor;
    • mantener el código;
    • probar en entornos distintos;
    • reutilizar componentes.

    Qué necesitamos entonces¶

    Una forma de acceso:

    • común;
    • razonablemente portable;
    • preparada para errores;
    • compatible con consultas seguras.

    Esa forma, en PHP, es PDO.

    5. Qué es PDO y por qué aparece en esta UT¶

    PDO significa PHP Data Objects.

    Es una capa de acceso a bases de datos que ofrece una API común para distintos gestores.

    ¿Qué nos aporta?¶

    • una forma unificada de conectar;
    • una forma común de lanzar consultas;
    • soporte para consultas preparadas;
    • mejor tratamiento de errores mediante excepciones;
    • posibilidad de reutilizar buena parte del código entre SQLite y MySQL.

    Qué no hace PDO¶

    PDO no elimina todas las diferencias entre SGBD.

    Por ejemplo:

    • algunos tipos de datos siguen siendo distintos;
    • algunas consultas avanzadas cambian;
    • algunas funciones SQL son propias de cada motor.

    Pero para una UT de introducción profesional, PDO es una decisión excelente.

    Idea clave¶

    Con PDO, muchas veces el cambio principal entre SQLite y MySQL está en:

    • el DSN de conexión;
    • detalles concretos del SQL;
    • el entorno donde vive la base de datos.

    El resto del patrón PHP puede mantenerse casi igual.

    6. Primer contacto con PDO¶

    6.1. Conexión con SQLite¶

    En SQLite la base de datos es un fichero.

    <?php
$pdo = new PDO('sqlite:' . __DIR__ . '/data/agenda.sqlite');

    Si el fichero no existe, SQLite puede crearlo.

    6.2. Conexión con MySQL / MariaDB¶

    Aquí necesitamos host, puerto, nombre de base de datos, usuario y contraseña.

    <?php
$dsn = 'mysql:host=db;port=3306;dbname=agenda;charset=utf8mb4';
$usuario = 'agenda_user';
$password = 'cambia_esto';

$pdo = new PDO($dsn, $usuario, $password);

    6.3. Configuración recomendable de PDO¶

    No conviene quedarse en la conexión mínima.
    Es mejor configurar algunos atributos desde el principio.

    <?php
$pdo = new PDO($dsn, $usuario, $password, [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
]);

    Qué significan¶

    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION¶

    Hace que los errores se gestionen como excepciones.

    Ventaja: - detectar fallos claramente; - evitar que la aplicación siga como si nada; - depurar mejor.

    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC¶

    Hace que las filas se devuelvan como arrays asociativos:

    [
    'id' => 1,
    'nombre' => 'Ana',
    'email' => 'ana@ejemplo.com'
]

    Eso suele ser más cómodo que manejar índices numéricos.

    6.4. Comprobar qué drivers PDO están disponibles¶

    <?php
print_r(PDO::getAvailableDrivers());

    Esto es útil cuando una conexión falla y sospechas que el driver no está instalado.

    Error típico¶

    Confundir:

    • PDO: la API de acceso;
    • el driver: la pieza concreta para un motor (pdo_sqlite, pdo_mysql, etc.);
    • el SGBD: SQLite, MariaDB/MySQL, PostgreSQL...

    3. ¿Para qué sirve PDO::FETCH_ASSOC?

    7. El DSN: la dirección técnica de la conexión¶

    El DSN es la cadena que describe cómo conectarse al origen de datos.

    Ejemplo SQLite¶

    sqlite:/ruta/al/fichero.sqlite

    Ejemplo MySQL¶

    mysql:host=db;port=3306;dbname=agenda;charset=utf8mb4

    Por qué es importante entenderlo¶

    Porque ahí se concreta:

    • qué motor usamos;
    • dónde está;
    • qué base de datos queremos;
    • qué codificación queremos.

    Error típico¶

    Pensar que si cambiamos de SQLite a MySQL solo cambia la contraseña.

    No.
    Cambia el modelo completo:

    • en SQLite apuntas a un fichero;
    • en MySQL apuntas a un servicio;
    • en MySQL entran en juego usuarios y permisos reales del SGBD.

    2. una base MySQL llamada biblioteca en host db, puerto 3306, con utf8mb4

    8. Una estructura mínima razonable para el proyecto¶

    Aunque sea una práctica pequeña, conviene evitar el caos.

    Estructura sugerida¶

    ut3-crud/
├── config/
│   └── database.php
├── public/
│   ├── index.php
│   ├── crear.php
│   ├── editar.php
│   └── borrar.php
├── src/
│   └── helpers.php
├── data/
│   └── agenda.sqlite
└── README.md

    Por qué así¶

    • config/ centraliza la conexión;
    • public/ contiene los puntos de entrada web;
    • src/ agrupa funciones auxiliares;
    • data/ guarda el fichero SQLite si usamos SQLite;
    • evitamos mezclarlo todo en un único archivo enorme.

    No buscamos arquitectura enterprise

    Esta UT no pretende convertir una práctica pequeña en un framework.
    Sí pretende que el código tenga un orden mínimo comprensible.

    9. Crear una conexión reutilizable¶

    config/database.php para SQLite¶

    <?php

declare(strict_types=1);

function getConnection(): PDO
{
    $databasePath = __DIR__ . '/../data/agenda.sqlite';

    $pdo = new PDO('sqlite:' . $databasePath, null, null, [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    ]);

    return $pdo;
}

    Versión equivalente para MySQL¶

    <?php

declare(strict_types=1);

function getConnection(): PDO
{
    $dsn = 'mysql:host=db;port=3306;dbname=agenda;charset=utf8mb4';
    $user = 'agenda_user';
    $password = 'cambia_esto';

    $pdo = new PDO($dsn, $user, $password, [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    ]);

    return $pdo;
}

    Observa lo importante¶

    • el nombre de la función es el mismo;
    • el resto del proyecto puede seguir llamando a getConnection();
    • el cambio de motor no obliga a reescribir toda la aplicación.

    10. Crear tablas desde PHP¶

    Uno de los criterios del RA pide crear bases de datos y tablas en el gestor utilizando el lenguaje de guiones.

    Eso significa que no basta con tocar la base de datos solo a mano con una herramienta visual. Debemos ser capaces de lanzar desde PHP el SQL necesario.

    Ejemplo SQLite: tabla contactos¶

    <?php

$pdo = getConnection();

$sql = <<<SQL
CREATE TABLE IF NOT EXISTS contactos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    nombre TEXT NOT NULL,
    email TEXT NOT NULL,
    telefono TEXT,
    created_at TEXT NOT NULL
)
SQL;

$pdo->exec($sql);

    Qué hace exec()¶

    exec() sirve para ejecutar sentencias SQL que no devuelven un conjunto de resultados como un SELECT.

    Por ejemplo:

    • CREATE TABLE
    • INSERT simple
    • UPDATE
    • DELETE

    Aunque para INSERT, UPDATE y DELETE con datos variables lo habitual será usar prepare().

    MySQL: misma idea, matices distintos¶

    <?php

$sql = <<<SQL
CREATE TABLE IF NOT EXISTS contactos (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL,
    telefono VARCHAR(30),
    created_at DATETIME NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
SQL;

$pdo->exec($sql);

    Qué estamos aprendiendo aquí¶

    No memorices cada palabra del SQL. Quédate con la idea:

    • desde PHP puedo enviar SQL al gestor;
    • la definición concreta de tabla cambia un poco según el motor;
    • el patrón mental es el mismo.

    Error típico¶

    Usar herramientas visuales para crear la tabla y luego no saber reproducir el proceso desde código.

    En clase pueden ayudarte, pero para el RA debes dominar el proceso desde PHP.

    11. Insertar datos: el primer paso del CRUD¶

    CRUD significa:

    • Create
    • Read
    • Update
    • Delete

    Supón que recibimos un formulario con:

    • nombre
    • email
    • teléfono

    Mal enfoque: concatenar directamente¶

    <?php
$sql = "INSERT INTO contactos (nombre, email, telefono, created_at)
        VALUES ('" . $_POST['nombre'] . "', '" . $_POST['email'] . "', '" . $_POST['telefono'] . "', datetime('now'))";
$pdo->exec($sql);

    Esto es mala idea porque:

    • mezcla lógica y datos de forma peligrosa;
    • es frágil si aparecen comillas;
    • abre la puerta a inyecciones SQL;
    • complica mantenimiento.

    Enfoque correcto: consulta preparada¶

    <?php
$sql = "INSERT INTO contactos (nombre, email, telefono, created_at)
        VALUES (:nombre, :email, :telefono, :created_at)";

$stmt = $pdo->prepare($sql);

$stmt->execute([
    ':nombre' => $nombre,
    ':email' => $email,
    ':telefono' => $telefono,
    ':created_at' => date('Y-m-d H:i:s'),
]);

    Por qué esto es mejor¶

    • separa estructura SQL y datos;
    • evita concatenaciones peligrosas;
    • mejora legibilidad;
    • hace el código más portable y profesional.

    Regla práctica

    Si una consulta usa datos que vienen del usuario o de una variable, piensa primero en prepare().

    12. Leer datos: SELECT y tratamiento de resultados¶

    Obtener todos los contactos¶

    <?php
$stmt = $pdo->query("SELECT id, nombre, email, telefono, created_at FROM contactos ORDER BY id DESC");
$contactos = $stmt->fetchAll();

    Mostrar resultados en HTML¶

    <table>
    <thead>
        <tr>
            <th>ID</th>
            <th>Nombre</th>
            <th>Email</th>
            <th>Teléfono</th>
        </tr>
    </thead>
    <tbody>
        <?php foreach ($contactos as $contacto): ?>
            <tr>
                <td><?= htmlspecialchars((string) $contacto['id']) ?></td>
                <td><?= htmlspecialchars($contacto['nombre']) ?></td>
                <td><?= htmlspecialchars($contacto['email']) ?></td>
                <td><?= htmlspecialchars($contacto['telefono'] ?? '') ?></td>
            </tr>
        <?php endforeach; ?>
    </tbody>
</table>

    Por qué usamos htmlspecialchars()¶

    Porque una cosa es consultar datos y otra mostrarlos con seguridad en HTML.

    Si un usuario ha guardado texto con caracteres especiales o incluso código HTML/JavaScript, escaparlo evita problemas de visualización y reduce riesgos de XSS.

    Idea muy importante¶

    • prepare() protege la consulta SQL.
    • htmlspecialchars() protege la salida HTML.

    Son problemas distintos.
    No sustituyen uno al otro.

    Leer una fila concreta¶

    <?php
$stmt = $pdo->prepare("SELECT * FROM contactos WHERE id = :id");
$stmt->execute([':id' => $id]);

$contacto = $stmt->fetch();

    Esto lo necesitaremos para la pantalla de edición.

    13. Actualizar datos: UPDATE¶

    Editar un registro es un ciclo muy común:

    1. leo el registro actual;
    2. muestro sus valores en un formulario;
    3. el usuario cambia datos;
    4. valido;
    5. lanzo UPDATE.

    Ejemplo¶

    <?php
$sql = "UPDATE contactos
        SET nombre = :nombre, email = :email, telefono = :telefono
        WHERE id = :id";

$stmt = $pdo->prepare($sql);

$stmt->execute([
    ':nombre' => $nombre,
    ':email' => $email,
    ':telefono' => $telefono,
    ':id' => $id,
]);

    Error típico¶

    Confiar en que el id recibido es correcto sin comprobar nada.

    Como mínimo conviene:

    • convertirlo al tipo esperado;
    • verificar que existe el registro;
    • usar consulta preparada;
    • gestionar el caso en que no haya coincidencia.

    14. Borrar datos: DELETE¶

    Ejemplo¶

    <?php
$stmt = $pdo->prepare("DELETE FROM contactos WHERE id = :id");
$stmt->execute([':id' => $id]);

    Buenas prácticas¶

    • usar método POST para operaciones destructivas;
    • no borrar por un enlace GET directo si puedes evitarlo;
    • pedir confirmación al usuario;
    • comprobar que el registro existe antes o después según diseño.

    Error típico¶

    Poner algo así:

    <a href="borrar.php?id=3">Borrar</a>

    y que la eliminación ocurra en cuanto se entra por URL.

    Es mejor:

    • mostrar un pequeño formulario;
    • enviar por POST;
    • ejecutar la acción solo si la intención es explícita.

    15. Validación de datos en servidor¶

    Uno de los errores más comunes cuando se empieza es pensar que la validación del navegador ya es suficiente.

    No lo es.

    Por qué no basta con HTML¶

    El usuario puede:

    • desactivar validaciones;
    • manipular la petición;
    • enviar datos desde otro cliente;
    • cometer errores que el navegador no entiende del todo.

    Validaciones básicas que sí deberías hacer¶

    • trim() para eliminar espacios sobrantes;
    • comprobar campos obligatorios;
    • validar email con filter_var;
    • limitar longitudes razonables;
    • asegurar que los identificadores son numéricos si corresponde.

    Ejemplo¶

    <?php

$errores = [];

$nombre = trim($_POST['nombre'] ?? '');
$email = trim($_POST['email'] ?? '');
$telefono = trim($_POST['telefono'] ?? '');

if ($nombre === '') {
    $errores[] = 'El nombre es obligatorio.';
}

if ($email === '' || filter_var($email, FILTER_VALIDATE_EMAIL) === false) {
    $errores[] = 'El email no es válido.';
}

if ($telefono !== '' && strlen($telefono) > 30) {
    $errores[] = 'El teléfono es demasiado largo.';
}

    Regla práctica¶

    Primero validas.
    Después consultas o guardas.
    No al revés.

    • nombre

    16. Seguridad básica en acceso a base de datos¶

    Este apartado es clave en la unidad. No buscamos convertir al alumnado en especialista de ciberseguridad, pero sí evitar hábitos peligrosos.

    16.1. No usar root en la aplicación¶

    Esto es una mala práctica muy común en prácticas rápidas.

    ¿Por qué no conviene?

    • root tiene permisos excesivos;
    • si algo falla o alguien explota una vulnerabilidad, el impacto es mayor;
    • no refleja un despliegue profesional.

    Mejor enfoque¶

    Crear un usuario específico para la aplicación con solo los permisos que necesite.

    Por ejemplo, para una app CRUD básica:

    • SELECT
    • INSERT
    • UPDATE
    • DELETE

    Quizá durante inicialización también: - CREATE - ALTER - INDEX

    Pero en producción conviene separar incluso eso si el despliegue está más maduro.

    16.2. Consultas preparadas¶

    Ya lo hemos visto, pero merece repetirlo:

    • no concatenes datos del usuario en el SQL;
    • usa prepare() y execute().

    16.3. Escapar la salida HTML¶

    No sirve de nada proteger la consulta si luego muestras sin control lo que hay en base de datos.

    16.4. No exponer errores técnicos al usuario final¶

    En desarrollo sí necesitas verlos.
    En producción no conviene mostrar mensajes técnicos completos.

    En vez de esto:

    SQLSTATE[HY000] [1045] Access denied for user...

    conviene registrar el error y mostrar un mensaje genérico.

    16.5. Separar configuración sensible¶

    Evita dejar credenciales repartidas por muchos archivos.

    Mejor:

    • centralizar conexión;
    • usar variables de entorno o un fichero de configuración fuera del repositorio cuando el entorno lo permita.

    16.6. Contraseñas de usuarios de aplicación¶

    Si la aplicación gestiona usuarios propios, las contraseñas no se guardan en texto plano.

    En PHP se usaría:

    • password_hash()
    • password_verify()

    En esta UT no es obligatorio montar un sistema completo de autenticación, pero sí conviene introducir la idea.

    16.7. Medidas básicas recomendables en una práctica¶

    Para esta UT consideraremos adecuado que el alumnado aplique al menos estas medidas:

    • usuario de BD no root;
    • consultas preparadas;
    • validación en servidor;
    • salida escapada con htmlspecialchars();
    • acciones destructivas por POST.

    Nivel esperado

    No exigimos una auditoría completa de seguridad.
    Sí exigimos evitar errores básicos graves.

    17. SQLite y MySQL: mismo patrón, entorno diferente¶

    Aquí está una de las ideas más valiosas de la unidad.

    El patrón general se mantiene¶

    1. conectar con PDO;
    2. crear tabla;
    3. preparar consulta;
    4. ejecutar con parámetros;
    5. obtener resultados;
    6. mostrarlos en HTML.

    Lo que cambia¶

    Aspecto SQLite MariaDB/MySQL
    Dónde vive la base de datos En un fichero En un servidor/servicio
    DSN sqlite:ruta/fichero.sqlite mysql:host=...;dbname=...;charset=utf8mb4
    Usuario y contraseña No suele requerir Sí
    Uso típico en aula Muy cómodo para arrancar Más realista profesionalmente
    Herramientas visuales Menos necesarias Muy comunes

    Ejemplo de reutilización¶

    Si tu aplicación usa una función getConnection(), el cambio puede reducirse a esa capa y a pequeños detalles SQL.

    Eso es exactamente lo que queremos que veas: el valor de una abstracción bien elegida.

    19. Consultas con filtros y parámetros¶

    En una aplicación real no siempre queremos “todos los datos”.

    Ejemplo: filtrar por estado¶

    <?php
$estado = $_GET['estado'] ?? 'todas';

if ($estado === 'todas') {
    $stmt = $pdo->query("SELECT * FROM tareas ORDER BY id DESC");
} else {
    $stmt = $pdo->prepare("SELECT * FROM tareas WHERE estado = :estado ORDER BY id DESC");
    $stmt->execute([':estado' => $estado]);
}

$tareas = $stmt->fetchAll();

    Qué estamos aprendiendo aquí¶

    • las consultas pueden ser dinámicas;
    • incluso cuando solo filtramos, seguimos usando parámetros;
    • separar condiciones claras mejora lectura y mantenimiento.

    Error típico¶

    Construir algo como:

    $sql = "SELECT * FROM tareas WHERE estado = '" . $_GET['estado'] . "'";

    Ya sabes por qué no.

    20. Gestión de errores y depuración¶

    Cuando trabajas con base de datos, los errores no solo vienen del PHP. También pueden venir de:

    • el driver;
    • el DSN;
    • permisos;
    • tabla inexistente;
    • nombre de columna incorrecto;
    • datos inválidos.

    Patrón básico con try/catch¶

    <?php

try {
    $pdo = getConnection();
    $stmt = $pdo->query("SELECT * FROM contactos");
    $contactos = $stmt->fetchAll();
} catch (PDOException $e) {
    echo "Ha ocurrido un error al acceder a la base de datos.";
}

    En desarrollo¶

    Durante desarrollo puede interesarte registrar o inspeccionar el error real.

    En producción¶

    No conviene mostrar el detalle técnico al usuario.

    Fallos muy comunes¶

    1. Driver no instalado¶

    Mensaje típico: el driver PDO específico no está disponible.

    2. DSN incorrecto¶

    Host erróneo, nombre de base de datos mal escrito, ruta SQLite incorrecta...

    3. Tabla no existe¶

    Has cambiado el nombre o no se ha ejecutado la creación.

    4. Permisos insuficientes¶

    El usuario de BD no puede hacer la operación solicitada.

    5. Datos incompatibles¶

    Longitudes, tipos o restricciones incumplidas.

    21. Verificación del funcionamiento¶

    El RA no se limita a “programar”. También exige verificar funcionamiento y rendimiento.

    ¿Qué significa verificar funcionamiento?¶

    Comprobar que:

    • la conexión funciona;
    • las tablas existen;
    • los datos se insertan;
    • los listados muestran lo esperado;
    • la edición modifica de verdad;
    • el borrado elimina lo correcto;
    • los errores de validación se detectan.

    Estrategia razonable de prueba en aula¶

    Para cada operación, prueba al menos:

    • caso correcto;
    • campo obligatorio vacío;
    • email inválido;
    • id inexistente en edición o borrado;
    • valores con caracteres especiales;
    • registros múltiples.

    Tabla de verificación mínima¶

    Operación Comprobación
    Conexión La app arranca sin error
    Crear tabla La tabla existe en el gestor
    Insertar Se añade una fila nueva
    Listar Los datos aparecen correctamente
    Editar La modificación se refleja
    Borrar El registro desaparece
    Validar Los errores se detectan antes de guardar

    22. Rendimiento básico: qué mirar sin complicarnos demasiado¶

    No buscamos optimización avanzada, pero sí una base profesional.

    Algunas ideas simples y útiles¶

    1. No abras conexiones de forma caótica¶

    Centraliza la conexión y reutiliza el patrón.

    2. Pide solo los datos necesarios¶

    Si solo necesitas id y nombre, no uses SELECT * por costumbre ciega en todas partes.

    3. Limita resultados si procede¶

    En listados largos, usar LIMIT tiene sentido.

    4. Añade índices cuando un campo se consulta mucho¶

    En esta UT basta con introducir la idea.

    5. Comprueba con datos reales de prueba¶

    Una app que funciona con 2 filas puede comportarse peor con 500.

    Ejemplo conceptual de índice¶

    Si buscas constantemente por email:

    CREATE INDEX idx_contactos_email ON contactos(email);

    Qué esperamos en esta UT¶

    No un tuning exhaustivo, sino que el alumnado:

    • entienda que el rendimiento existe como criterio;
    • sepa hacer comprobaciones básicas;
    • no programe de espaldas a la realidad del volumen y de las consultas.

    Aunque el corazón de la UT está en PHP + PDO, las herramientas visuales ayudan mucho.

    Para qué sirven¶

    • inspeccionar tablas;

    Úsalas como apoyo visual y de verificación, no como sustituto del proceso programado.

    24. Ejemplo completo: alta de contacto con validación y PDO¶

    A continuación tienes un ejemplo de una página de alta sencilla.

    <?php

declare(strict_types=1);

require_once __DIR__ . '/../config/database.php';

$errores = [];
$nombre = '';
$email = '';
$telefono = '';

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $nombre = trim($_POST['nombre'] ?? '');
    $email = trim($_POST['email'] ?? '');
    $telefono = trim($_POST['telefono'] ?? '');

    if ($nombre === '') {
        $errores[] = 'El nombre es obligatorio.';
    }

    if ($email === '' || filter_var($email, FILTER_VALIDATE_EMAIL) === false) {
        $errores[] = 'El email no es válido.';
    }

    if (empty($errores)) {
        $pdo = getConnection();

        $stmt = $pdo->prepare("
            INSERT INTO contactos (nombre, email, telefono, created_at)
            VALUES (:nombre, :email, :telefono, :created_at)
        ");

        $stmt->execute([
            ':nombre' => $nombre,
            ':email' => $email,
            ':telefono' => $telefono,
            ':created_at' => date('Y-m-d H:i:s'),
        ]);

        header('Location: index.php?ok=1');
        exit;
    }
}
?>

<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">
    <title>Nuevo contacto</title>
</head>
<body>
    <h1>Nuevo contacto</h1>

    <?php if ($errores): ?>
        <ul>
            <?php foreach ($errores as $error): ?>
                <li><?= htmlspecialchars($error) ?></li>
            <?php endforeach; ?>
        </ul>
    <?php endif; ?>

    <form method="post">
        <label>
            Nombre:
            <input type="text" name="nombre" value="<?= htmlspecialchars($nombre) ?>" required>
        </label>

        <label>
            Email:
            <input type="email" name="email" value="<?= htmlspecialchars($email) ?>" required>
        </label>

        <label>
            Teléfono:
            <input type="text" name="telefono" value="<?= htmlspecialchars($telefono) ?>">
        </label>

        <button type="submit">Guardar</button>
    </form>
</body>
</html>

    Qué conviene observar en este ejemplo¶

    • se separa la conexión en otro archivo;
    • se validan datos antes de insertar;
    • se usa prepare() y execute();
    • se escapan mensajes y valores al reimprimirlos;
    • tras guardar, se redirige;
    • no se concatena SQL con entrada del usuario.

    25. Errores y confusiones típicas de esta UT¶

    1. “Si uso PDO, ya no tengo que pensar en seguridad”¶

    Falso. PDO ayuda mucho, pero debes usarlo bien.

    2. “Si el formulario tiene required, ya he validado”¶

    Falso. Falta validación de servidor.

    3. “Si funciona con SQLite, ya está listo para cualquier cosa”¶

    No necesariamente. SQLite sirve muy bien para aprender y prototipar, pero el contexto cambia con MySQL.

    4. “phpMyAdmin me crea la tabla, así que ya he cumplido”¶

    No del todo. Debes saber hacerlo desde PHP cuando el ejercicio o criterio lo pide.

    5. “prepare() sirve para cualquier problema”¶

    No. Protege la consulta SQL, no la salida HTML.

    6. “SELECT * siempre está bien”¶

    A veces sirve, pero no conviene convertirlo en costumbre automática.

    7. “La base de datos ya validará todo”¶

    La base de datos ayuda con restricciones, pero la aplicación debe validar antes.

    26. De SQLite a MySQL: lo que debes saber transferir¶

    Si entiendes bien esta UT, deberías ser capaz de:

    • cambiar el DSN;
    • pasar de un fichero SQLite a un servicio MySQL;
    • ajustar la creación de tabla;
    • mantener el patrón prepare() + execute();
    • seguir validando igual;
    • seguir escapando salida igual.

    Pregunta de madurez técnica¶

    Si mañana te cambian el almacenamiento de una práctica de SQLite a MariaDB,
    ¿sabrías localizar qué parte del proyecto adaptar y cuál debería permanecer igual?

    Si la respuesta es sí, vas en la dirección correcta.

    27. Resumen final de la unidad¶

    Qué ideas deben quedar claras:

    1. una aplicación web real necesita persistencia;
    2. los SGBD más usados no son idénticos;
    3. PDO ofrece una forma profesional de acceder a datos desde PHP;
    4. el corazón práctico es el patrón CRUD;
    5. la seguridad básica pasa por:
    6. consultas preparadas;
    7. validación en servidor;
    8. salida escapada;
    9. usuario de BD con permisos ajustados;
    10. SQLite y MySQL permiten aprender el mismo patrón en contextos distintos;
    11. además de programar, hay que verificar funcionamiento.
