    Práctica 1 · Formulario de presupuesto de alojamiento web¶

    1. Qué vas a construir¶

    Vas a desarrollar una miniaplicación PHP que muestre un formulario, reciba los datos enviados por POST, los valide en el servidor y genere una respuesta dinámica con un presupuesto orientativo de hosting.

    No se busca una web “bonita”, sino una solución clara, funcional y bien pensada.

    2. Qué demuestra esta práctica¶

    Con esta práctica debes demostrar que sabes:

    • relacionar HTML y PHP en una misma aplicación;
    • procesar formularios en servidor;
    • usar estructuras de control;
    • definir y utilizar funciones;
    • validar datos de entrada;
    • generar una salida dinámica comprensible.

    Criterios del RA5 trabajados¶

    • CE2. Relación entre lenguaje de servidor y lenguaje de marcas.
    • CE3. Sintaxis básica del lenguaje.
    • CE4. Estructuras de control.
    • CE5. Definición y uso de funciones.
    • CE6. Uso de formularios para introducir información.

    3. Contexto funcional¶

    Una pequeña empresa quiere una página sencilla para que un posible cliente pida un presupuesto inicial de alojamiento web.

    La aplicación no contrata nada ni guarda todavía los datos en base de datos. Su misión es:

    1. recoger la información del formulario;
    2. comprobar si los datos son válidos;
    3. calcular un precio orientativo;
    4. devolver una respuesta clara al usuario.

    4. Requisitos obligatorios¶

    Tu aplicación debe incluir, como mínimo, estos campos:

    • Nombre de contacto
    • Correo electrónico
    • Tipo de plan
    • Básico
    • Profesional
    • Empresa
    • Meses de contratación
    • Copia de seguridad avanzada
    • Soporte prioritario

    Además, debe cumplir estos requisitos:

    1. usar un formulario enviado por POST;
    2. validar los datos en PHP;
    3. mostrar mensajes de error claros cuando algo no sea válido;
    4. conservar los valores ya introducidos si hay errores;
    5. calcular y mostrar:
    6. plan elegido,
    7. extras seleccionados,
    8. importe base,
    9. recargos,
    10. total final;
    11. utilizar al menos:
    12. una estructura condicional,
    13. una estructura de recorrido,
    14. una o varias funciones propias.

    5. Requisitos técnicos mínimos¶

    Obligatorio¶

    • Al menos un archivo .php que genere HTML dinámico.
    • Tratamiento correcto de $_POST.
    • Validación básica de datos.
    • Funciones propias para separar lógica.
    • Código ordenado y fácil de seguir.

    Muy recomendable¶

    • Separar funciones auxiliares en un archivo includes/funciones.php.
    • Evitar leer índices inexistentes con ??.
    • Usar trim() en campos de texto.

    6. Tarifas orientativas¶

    Puedes usar estas tarifas o unas equivalentes si las explicas:

    • Básico: 5 €/mes
    • Profesional: 9 €/mes
    • Empresa: 15 €/mes

    Extras:

    • Copia de seguridad avanzada: +2 €/mes
    • Soporte prioritario: +3 €/mes

    7. Estructura orientativa¶

    practica-1/
├── index.php
├── procesar.php
└── includes/
    └── funciones.php

    También puedes resolverla en un solo archivo si el resultado queda claro y ordenado.

    8. Flujo esperado¶

    flowchart TD
    A[Usuario abre el formulario] --> B[Rellena datos]
    B --> C[Envía por POST]
    C --> D[PHP valida la información]
    D -->|Hay errores| E[Se vuelve a mostrar el formulario con mensajes]
    D -->|Todo correcto| F[PHP calcula el presupuesto]
    F --> G[Se muestra el resumen final]

    9. Entrega¶

    Debes entregar:

    • carpeta o .zip con el proyecto;
    • una captura del formulario;
    • una captura de un caso correcto;
    • una captura de un caso con errores de validación;
    • opcionalmente, un README.md breve con la estructura y decisiones tomadas.

    10. Errores típicos a evitar¶

    Leer $_POST sin comprobar nada¶

    $nombre = $_POST['nombre'];

    Mejor enfoque:

    if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $nombre = trim($_POST['nombre'] ?? '');
}

    Confiar solo en la validación del navegador¶

    El navegador ayuda, pero la validación importante en esta práctica está en servidor.

    Perder los datos al mostrar errores¶

    Si el usuario se equivoca, no debería tener que rellenar todo otra vez.

    Mezclar cálculo y presentación sin orden¶

    El flujo recomendado es:

    1. recibir;
    2. validar;
    3. calcular;
    4. mostrar.

    11. Ampliaciones opcionales¶

    Si acabas antes, puedes añadir alguna mejora:

    • descuento por contratación anual;
    • mensaje distinto según el plan;
    • desglose más detallado del cálculo;
    • CSS básico;
    • validación más estricta del correo.

    12. Cómo se evaluará esta práctica¶

    La evaluación será la misma tanto si cursas presencial como si cursas semipresencial.

    El profesor valorará dos cosas:

    1. el producto entregado y su funcionamiento;
    2. una validación breve de autoría y comprensión, que podrá hacerse en clase o por videollamada.

    En esa validación se te puede pedir que:

    • ejecutes tu práctica;
    • señales dónde se procesa el formulario;
    • expliques una función tuya;
    • hagas una mini modificación muy pequeña, por ejemplo:
    • añadir un nuevo plan,
    • cambiar un recargo,
    • exigir un mínimo de 3 meses,
    • mostrar un mensaje especial si el total supera cierta cantidad.

    13. Rúbrica de evaluación de la práctica¶

    Cada bloque se valora con 0, 1 o 2 puntos.

    Bloque 0 puntos 1 punto 2 puntos
    1. Funcionamiento técnico La práctica no funciona o falla en lo esencial. Funciona parcialmente, con errores de flujo o resultados poco fiables. Funciona bien en lo esencial: recibe datos, procesa y muestra un resultado coherente.
    2. PHP, lógica y organización El código está muy desordenado o apenas usa PHP de forma real. Usa PHP y algo de lógica, pero con organización mejorable. Usa PHP de forma clara, con estructuras de control y funciones útiles.
    3. Validación de entrada No valida o valida de forma muy pobre. Valida lo básico, pero con huecos o mensajes poco claros. Valida bien los datos importantes, muestra errores comprensibles y conserva valores si procede.
    4. Comprensión del trabajo No sabe explicar qué archivo procesa, qué hace el formulario o cómo calcula. Explica una parte, pero con dudas importantes. Explica con claridad el flujo completo y localiza las partes clave del código.
    5. Autoría y mini variante No sabe hacer una modificación mínima ni orientarse en su propio código. Hace la variante con mucha ayuda o de forma incompleta. Resuelve o encamina bien una mini variante sencilla sobre su propia práctica.

    Interpretación rápida¶

    • 0 a 4 puntos → insuficiente
    • 5 a 6 puntos → suficiente
    • 7 a 8 puntos → bien / notable
    • 9 a 10 puntos → notable alto / sobresaliente

    Condición mínima recomendable¶

    Para considerar la práctica superada, debe cumplirse esto:

    • el producto funciona en lo esencial;
    • el alumno demuestra comprensión básica de su propio código;
    • supera una validación breve de autoría.

    14. Checklist del alumno antes de entregar¶

    • Mi formulario envía datos por POST.
    • Estoy comprobando la petición antes de leer $_POST.
    • Uso al menos una estructura condicional.
    • Uso al menos una función propia.
    • Valido los datos en PHP.
    • Si hay errores, el usuario los entiende.
    • El presupuesto final se calcula correctamente.
    • Soy capaz de explicar mi código y hacer una modificación pequeña.
